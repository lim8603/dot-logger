## RV-160

**[리뷰어]** 32생산자·128채널·16출력에는 손실 행 639,616개가 등록된다. 각 파일의 시작·최종 체크포인트가 9,994청크씩 필요하다. facade가 손실 report 수는 늘렸지만 파일당 최대 4,096청크와 인덱스 4 MiB를 고정했다. `plan()`의 산정과 `SegmentLog::new`의 검증이 어긋났다.

**[처리담당]** 저장 경로의 체크포인트 인덱스 계산을 계획 단계에서도 사용한다. 제어 청크와 인덱스에 필요한 양을 산정하고, 애플리케이션 기록에 기존 여유를 보존한다. 덧셈·곱셈은 오버플로를 검사한다. 원래 구성의 시작 실패와 축소 재현을 확인했다. 수정 뒤 단일 출력의 128생산자·128채널 회귀가 기록·종료·native 판독을 마쳤고 P3 대표 구성도 시작했다. 관리 경로만 바뀌었다. 공개 타입·파일 형식·RT 호출 경로에는 변경이 없다. [EV-097](../verification_evidence.md#ev-097)

## RV-161

**[리뷰어]** 실제 P3 쓰기 구간에서 동일한 제품의 과거 Query 한 페이지는 빠르게 응답했지만, 쓰기가 60초 창에 맞춰 수락되지 않았다. 최종 동기화까지 payload 처리량은 430.79 MB/s였고 제어 루프는 deadline miss 7회였다. 닫힌 1,263개 파일에서 기록 7,007,700건을 대조했고, 파일 추가 바이트 25.90 GB를 관측했다. 출력별 첫·마지막 파일 32개에서 손실 청크 직렬화가 558.19 MB였다. 파일 손실 체크포인트의 비용을 포함한 최신 제품의 재측정이며 EV-064~070의 당시 제품 결과를 보존한다.

**[처리담당]** T7과 TASK-031에 연결했다. 동일한 산출량에서 손실 체크포인트 비용을 분리하고, 승인된 P3 쓰기 부하를 충족하는 구성에서 P5를 다시 판정한다. 이번 변경은 시작 회귀의 범위에서 수락했다. [EV-097](../verification_evidence.md#ev-097)

**[처리담당 · 개발 반입]** 수용했다. 한 part를 쓸 때마다 청크를 닫았고, 대형 구성에서는 파일당 baseline과 final만 예약돼 주기 sync가 다음 파일로 회전했다. `SegmentWriter`는 연속 loss part를 크기 상한 안에서 묶는다. facade는 baseline·final과 별도로 주기 관측 두 번의 part·청크·인덱스를 산정한다. 보존 예산은 인코더가 낼 수 있는 canonical payload 상한으로 계산한다. reader와 recovery는 원래 한 part당 한 청크인 파일도 읽는다.

**[처리담당 · 재측정]** 8 GiB 제한 회차에서 예열 포함 70초분을 76.93초에 수락했다. 쓰기와 겹친 조회 40건의 p95는 4.72ms였다. 이 조건에서는 P3가 여전히 미달이어서 RV-161과 정식 P5를 유지한다. 같은 제한의 P0 단순 writer와 제품 쓰기 지연을 대조할 수 있다. [EV-098](../verification_evidence.md#ev-098)
