## 1. 목표와 첫 적용 대상

Linux·macOS·Windows에서 사용할 Rust 로보틱스 로깅·텔레메트리 라이브러리와 모니터링 클라이언트를 제작한다. Linux + PREEMPT_RT의 실시간 최적화·검증 목표를 유지한다. 첫 적용 대상은 **dot-probe**다.

**핵심 가치:** 높은 기록 성능과 함께, 사용 중 실제 부하·병목·검증된 처리 범위를 확인하고 개발자가 로그의 양·주기·대상을 조절한 효과를 다시 측정할 수 있게 한다. 운영 계측·리포트·간편 점검·개발자 조절 지원은 이 라이브러리의 핵심 강점으로 삼는다. 실제 관측·별도 검증·추정의 구분과 계측 자체의 자원 예산은 유지한다.

Human이 사용자 식별자 lim8603과 solo(1인 개발)를 확인했다. 프로필·개인 상태·로그를 초기화했으며 공식 산출물 언어는 생성 전에 확인할 잔여 운영 항목이다.

## 6. 근거

- Human이 미니 UPS 등의 신호를 받으면 중요 파일 우선순위로 기록하는 기능 추가를 요청했다. 후속 답변으로 약 3초는 **UPS 신호 발생부터 실제 전원 차단까지 전체 시간**이라고 확인했다. FR-018·§17에 반영한다. 앞선 핵심 API 세부 권고안 전체를 승인한 답변으로 해석하지 않는다.
- 이어 Human이 해당 기능을 옵션으로 제공하고 **기본 활성화 상태는 비활성**으로 지정했다. FR-018 지원 기능과 배포별 사용 여부를 구분한다.

- Human이 Linux·macOS·Windows 크로스 플랫폼 지원을 필수로 추가했다(NFR-007·ADR-006). 이어 대표 센서 구성을 UHD급2D LiDAR1개·카메라4개로 일반화하도록 지시했다. 기존 성능 기준선은 설계 목표로 유지하고 새 카메라/센서 부하와 각 OS의 실측 대응은 Design에서 확인한다.

- Human은 성능뿐 아니라 사용 중 한계를 측정·확인하고 개발자가 로그량을 조절할 수 있는 점을 라이브러리의 강점으로 삼도록 지정했다. 핵심 가치·FR-014/016·FR-017·NFR-006·§13.5에 반영했다. 질문 프리셋 세부·수치 목표·UI/API·관측 정확도는 여전히 후속 설계 사항이다.

- Human은 질문 프리셋과 PC 성능에 따른 기본 설정 추천을 제안하고, 실제 측정을 별도 작업으로 해야 해 잘 하지 않게 되는 문제를 설명했다. FR-015·FR-016·§14에서 설정·계측·결과 해석을 제품 내 흐름으로 연결하는 안을 구체화했다. 도구/시험 실행이나 새 기본값을 확정한 것은 아니다.

- Human의 PC 사양·로그 양·시간 간격을 활용한 사용률/버틸 시간 리포트 아이디어를 FR-014·§13의 기능 제안으로 기록했다. 구현 가능성은 조사했으며 자동 보정 시험 실행·예측 보장·기능 우선순위를 확정한 것은 아니다.

- Human은 통합 사양안에 전반적으로 긍정하면서 버퍼 예산 증액과 성능 관계를 질문했다. §12.3의 메모리 수치를 R1 기준2 GiB 및 용량별 비교 시험으로 수정 제안했다. 새 용량의 제품 기본값·구체 배분은 미확정이다.

- Human의 「여러 조사 결과를 거쳐 우리 로거 스펙을 정해본다면?」 요청으로 §12 통합 사양안을 작성했다. 새로운 수치·설계 후보는 AI 제안이며 기존 결정의 변경·승인으로 취급하지 않는다.

- Human의 후속 요청: 다수 스레드의 동시 로깅과 목적에 따른 다수 파일 로깅을 지원해야 함. FR-012·FR-013와 §11에 반영. 구현 구조·지원 개수·정량 기준은 미선정.

- Human의 공개 성능표 확인 후 의견: RAM 수락만 빠른 것으로는 충분하지 않으며, OS I/O와 데이터가 활용되어 가치를 갖기까지의 실제 경로 성능을 목표로 한다. 기존 조사에서 크게 벗어나지 않는 수치안을 원함. 실사용 성능·TCP 조사(비공개 원시 근거: `imported_context/research_2026-10-25_end_to_end_tcp.md`). 숫자나 네트워크 장비는 미확정.

- Human의 2026-10-25 프로젝트 목표와 조사·순차 질문 요청.
- Human의 Q7 답변: 순간 처리량과 하드웨어별 저장량을 별개로 보고, SSD를 기본으로 가정하며, 원본 연속/순환·이벤트 보존도 옵션으로 제공. [ADR-004](../03_design_artifacts/adrs/ADR-004_processing_and_storage_budgets.md)에 기록.
- Human의 2026-10-25 Q6 답변: UHD급 이상, R2000 UHD 1개, 모터 10개 이상(2D2S·리프트·컨베이어), 각종 센서, 3D solid-state 센서 가능성, RealSense 4개를 가정한 처리 규모를 검토 요청. 설치 사양이나 처리량 수치까지 확정한 것은 아님.
- Human의 2026-10-25 Q5 답변 「1」 및 「ROS2 호환은 Probe 프로젝트 적용 후, 나중에 고려하자」. 자체 기록·조회·재생을 첫 적용 범위로 하고 ROS 2 연동 검토는 T1로 이월했다.
- Human의 2026-10-25 Q4 답변: 상태·오류 로그, 위치·속도·배터리 수치, 이미지·점군 원본을 확인. 「ros2_bag 같은것도 가능할까?」는 연동 가능성 검토 요청으로 기록하며 채택 결정으로 간주하지 않음.
- Human의 2026-10-25 Q1 답변 「1」: [ADR-002](../03_design_artifacts/adrs/ADR-002_rt_logging_never_waits_for_storage.md). 로깅으로 RT 제어를 대기시키지 않으며, 중요도별 보존·손실 정책은 별도 확정한다.
- Human의 2026-10-25 Q2 답변 「1」: ADR-002 보완 1. 버퍼 부족 시 중요 기록을 우선 보존한다. 분류 기준과 구체 손실·내구성 정책은 후속 확인한다.
- Human의 2026-10-25 후속 의견으로 정책 옵션화를 검토한 뒤, 「응, 세번째 질문도 기본값은 1」로 지원 방향과 기본값을 확정했다. 현재 기준은 [ADR-003](../03_design_artifacts/adrs/ADR-003_configurable_policies_and_defaults.md)이며 ADR-002를 대체한다.
- [INT-001](intents/INT-001_realtime_robotics_logging.md).
- 초기 조사(비공개 원시 근거: `imported_context/research_2026-10-25_logging_telemetry.md`). 외부 사실·로컬 dot-probe 관측·AI 가설을 구분했으며 후보 채택은 미정이다.

## 7. 확정된 정책 옵션과 기본값

기준: ADR-003. 라이브러리의 선택 가능한 정책과 기본값을 구분한다. 첫 적용 대상 dot-probe도 아래 기본안을 사용한다.

| 항목 | 지원 옵션 | 기본값 |
|------|-----------|--------|
| Q1: 기록 시 대기 | 무대기 / 제한 시간 대기 | 무대기 |
| Q2: 부족 시 보존 | 중요 기록 우선 / 동일 취급 | 중요 기록 우선 |
| Q3: 보존 중요도 분류 | 로그 레벨과 별도로 지정 / 로그 레벨 기반 | 로그 레벨과 별도로 보존 중요도 지정 |

RT용 호출은 무대기 계약을 유지한다. 제한 시간 대기는 일반 호출에 제공하는 옵션이며, 모든 조합을 RT용으로 허용하는 것은 아니다.

### 후속 설계 사항 — 미확정

- 설정 단위(핸들·채널·이벤트)와 초기화/런타임 변경 범위.
- 버퍼 구조·용량·예약과 포화 시의 세부 처리.
- 중요도 단계, 별도 중요도 생략 시 기본값, 레벨 매핑과 병행할 때의 우선순위.
- 조합별 메모리 상한, 호출 지연, 실패 관측 및 검증 기준.

초기 조사에서 제시한 레벨 매핑 후 명시값 우선 적용은 가능한 세부 설계안이다. 이번 「기본값 1」선택을 그 병행 규칙까지 승인한 것으로 해석하지 않는다.

### 조사 근거

- 대기/폐기 정책의 옵션화 사례: [tracing-appender 공식 설정 API](https://docs.rs/tracing-appender/latest/tracing_appender/non_blocking/struct.NonBlockingBuilder.html).
- 큐의 생성 시 고정 용량과 포화 시 오류 반환: [rtrb 공식 API](https://docs.rs/rtrb/0.4.0/rtrb/).

해당 프로젝트들이 dot-logger의 정책 조합 전체를 제공하거나 RT 요구를 충족한다는 의미는 아니다.

## 8. 첫 적용의 기록 데이터와 rosbag2 검토

| 데이터 범주 | 확인된 예 | 남은 정보 |
|-------------|-----------|-----------|
| 로그·이벤트 | 상태·오류 로그 | 스키마·크기·발생량·중요도 지정 |
| 수치 텔레메트리 | 위치·속도·배터리 | 채널 수·값 개수·빈도·시간 정밀도 |
| 대용량 센서 원본 | 이미지·점군 | 센서 수·해상도/포맷·건당 크기·빈도·소유권/수명 |

Q4의 데이터 범주는 확인됐다. 수집 API, 파일 저장, DB 저장의 구체 매핑은 확정하지 않았다. 원본 센서 기록이 포함된다는 사실을 모든 바이트를 시계열 DB에 넣거나 RT 호출 안에서 복사·인코딩하는 결정으로 해석하지 않는다.

첫 적용은 rosbag과 같은 자체 시간 기반 기록·조회·재생 기능으로 확정했다(FR-010). **ROS 2 파일 호환과 토픽 실시간 연동은 dot-probe 첫 적용 완료 후 검토한다(T1).** MCAP·SQLite 등의 파일 형식과 재생 API·출력 대상은 미선정이다. ROS 2 호환을 나중에 검토한다는 결정은 MCAP 자체를 후보에서 제외한다는 뜻이 아니다.

공식 출처, 포맷·타입·CDR·메타데이터 조건 및 검증 후보는 rosbag2 연동 조사(비공개 원시 근거: `imported_context/research_2026-10-25_rosbag2_interop.md`)에 보관했다. 성능·호환성 검증은 아직 실행하지 않았다.

## 9. 대표 로봇의 설계 부하 시나리오

Q6의 대표 구성을 후속 Human 요청으로 제품명 대신 UHD급2D LiDAR 센서1개·카메라 센서4개로 일반화했다. 모터10개 이상·기타/3D 센서 가능성은 유지한다. 설치 완료 장비나 라이브러리의 최대 센서 수를 뜻하지 않는다.

| 구성 | Human이 제시한 설계 가정 | 남은 정보 |
|------|-------------------------|-----------|
| 처리 규모 | UHD급 이상 | 해상도·저장 포맷·fps·동시 입력·지속/순간 부하 |
| 2D LiDAR 센서 | UHD급 1개 | 정확 장비·출력 패킷·측정 밀도/주기 |
| 모터 | 10개 이상, 2D2S·리프트·컨베이어 등 | 축 수·샘플 크기·필드·샘플링 주기 |
| 카메라 센서 | 4개 사용 가정 | 정확 장비·RGB/depth/IR 등의 스트림·해상도·fps·저장 포맷 |
| 기타·3D 센서 | 각종 센서 및 3D solid-state 센서 사용 가능성 | 종류·대수·points/s·필드·크기·주기 |

센서 용량 조사(비공개 원시 근거: `imported_context/research_2026-10-25_sensor_volume.md`)와 계산 JSON(비공개 원시 근거: `imported_context/research_2026-10-25_sensor_volume_calculations.json`)에 공식 사실·당시 Human 입력·산정 가정을 구분했다. 이 자료는 제품명이 있던 과거 조건부 조사다. P+F R2000 UHD라는 당시 가정에서 UHD는 Ultra High Density로, 3840×2160 영상 해상도와 다르다. 정확한 장비는 미확정이다.

과거 RealSense 4대 가정의 조건부 무압축 RGB-D 예시는 720p RGB+depth @30 fps에서 약553 MB/s, RGB1080p+depth720p @30 fps에서 약968 MB/s다. 원본 전량을 연속 보존하면 각각 약48/84 TB/24h가 된다. **이 수치는 계산 시나리오이며 실측값·확정 성능 목표·24시간 전량 저장 요구가 아니다.** 현재 일반 카메라4개 구성의 확정 사양으로 재사용하지 않는다. 압축·메타데이터·인덱스·추가 센서·정렬·장치 버스 특성은 별도다.

Q7에서 입력·처리 성능과 하드웨어별 저장 예산을 분리하고, 저장 방식은 옵션으로 제공하며 SSD를 기본 가정으로 하도록 확정했다(ADR-004). 24시간 전량 보존을 수락 조건으로 삼지 않는다. 실제 처리량·지속시간·메모리·저장·조회/재생 동시 부하의 수락 기준은 후속 합의한다.

## 10. 처리 성능·저장 예산·보존 옵션의 분리

기준: ADR-004. Q7의 전량/순환 보존 택일 질문은 종료했다. 사용자가 적용 환경에 맞게 설정할 정책을 제품 전체의 단일 동작으로 다시 선택받지 않는다.

| 축 | 정의·평가 방향 | 설정/남은 결정 |
|----|---------------|----------------|
| 입력 수락 | bytes/s·records/s, payload 크기, 수락 지연·실패, 부하 지속시간 | 생산자 수·burst 크기·지속시간·버퍼 예산 |
| 내부 처리 | 지정한 직렬화 등 처리 단계 완료량·지연, CPU·메모리 | 단계의 경계·포맷·기능 조합·수치 목표 |
| 영속 저장 | SSD의 파일 쓰기·영속 동기화 완료량·지연 | SSD·파일 시스템·동기화·동시 조회/재생 조건 |
| 전송·활용 | 수신 측에서 소비 가능한 데이터 제공·조회 응답·재생 출력의 완료량·지연 | 경로별 완료 경계·링크·CPU·동시 부하·지연/자원 예산 |
| 보존 | 연속 기록·순환 기록·이벤트 전후 구간 보존 옵션 | 기본 모드·최대 사용 용량·보존 기간·이벤트 창 |
| 과부하 | 수락 실패·정책 폐기·저장 실패를 구분해 관측 | 중요도와 모드별 포화 규칙·카운터·알림 API |

SSD는 기본 저장 매체의 가정이며 NVMe나 특정 모델, 용량, 수치 성능을 선택한 것은 아니다. 처리 성능을 평가하는 입력·처리 부하와, 특정 SSD에서 실제로 지속 기록할 수 있는 양 및 보존 기간을 별도로 보고한다.

모드·용량·기간·압축 등의 설정 단위와 런타임 변경 범위는 설계안으로 묶어 제시한다. 필요한 실제 하드웨어/부하 값은 대표 검증 프로필을 정할 때 수집하며, 기본값과 수락 기준은 아직 미정이다.

Human의 후속 의견으로 성능 평가의 주된 목적을 **선택한 경로에서 데이터가 실제 활용 가능한 상태가 되기까지의 성능**으로 구체화했다. RAM 수락·호출 지연과 단계별 수치는 병목 분석에 사용하고, 저장·전송·조회·재생의 실제 경로에서 완료량·지연·손실·자원 사용을 함께 평가한다. 모든 데이터를 모든 경로로 보낸다는 뜻은 아니다.

Q8의 방향 답변은 받았으며, 호출 시간 숫자만 다시 요청하지 않는다. AI가 기존 공개 조사와 같은 하드웨어의 기준 성능에 근거한 평가 프로필·초기 수치안을 준비한다. 수치·완료 경계·동시 부하·수락 기준의 승인은 아직 없다. 조사와 상세화 초안(비공개 원시 근거: `imported_context/research_2026-10-25_end_to_end_tcp.md`).

## 11. 다중 스레드·목적별 다중 파일 기록

Human이 여러 생산자 스레드의 동시 로깅과 목적별 여러 파일 기록을 기능 요구로 추가했다. 하나의 스레드가 여러 목적의 데이터를 기록하거나 여러 스레드가 같은 목적의 기록 대상에 모이는 사용을 지원한다. 스레드 식별과 논리 기록 대상은 구분하며 스레드마다 파일 하나를 강제하지 않는다. 다중 프로세스가 같은 파일에 직접 쓰는 지원까지 결정한 것은 아니다.

목적별 구성 예시는 다음과 같다. 논리 대상 이름과 파일 형식은 설명용이며 확정 API·포맷이 아니다.

| 논리 기록 대상 예 | 생산자 예 | 출력 예 |
|-------------------|-----------|---------|
| 상태·오류 | 제어·통신·진단 스레드 | 상태·오류 파일 |
| 모터 수치 | 여러 축의 제어·수집 스레드 | 모터 텔레메트리 파일 |
| 센서 원본 | 카메라·LiDAR 수집 스레드 | 센서별 또는 세션별 파일 |

다중 스레드·다중 파일에서도 ADR-003의 RT 무대기 계약과 별도 보존 중요도, ADR-004의 저장 예산·보존 옵션을 유지한다. 큐 구조·소비자 수·파일별 전용 작업자·실행기는 선택하지 않았다.

후속 설계안에는 목적/채널/컴포넌트 등의 분류·필터와 기록 대상 매핑, 대상별 회전·보존·버퍼/동기화 정책의 설정 범위를 묶어 제시한다. 한 기록의 여러 대상 중복 출력, 런타임 재설정, 느리거나 실패한 대상의 영향 격리, 대상별 완료·폐기·실패 카운터는 상세화 후보이며 세부 계약·기본값은 미정이다. 스레드 내부·채널 내부·채널 간 순서와 타임스탬프/시퀀스 규칙도 설계에서 명시해야 하며, 모든 스레드·파일의 전역 순서 보장을 가정하지 않는다.

성능 평가 초안에는 단일 스레드/단일 파일 기준과 함께 **다중 스레드→단일 파일**, **다중 스레드→다중 파일**, **작은 로그와 대용량 원본 혼합**, **특정 파일에 편중된 부하**, **파일 회전·조회·전송 동시 수행**을 포함한다. 스레드·파일 수별 확장성, 합계/대상별 완료 처리량·지연·손실·미처리량, CPU·메모리·파일 디스크립터 사용, 제어 주기 영향과 레코드 무결성을 확인한다. 지원 개수·시험 매개변수·손실/순서 판정·수락 수치는 후속 합의한다.

## 12. 초기 통합 사양안 — 제안 0.1

### 12.1 상태와 목적

**현재 상태: 2026-10-25 Human 「확정」으로 조건부 성능·자원 목표/R1/P0~P6를 설계 기준선으로 승인했다.** [ADR-005](../03_design_artifacts/adrs/ADR-005_design_baseline_and_deferred_decisions.md)를 따른다. 이후에도 기술/구현 후보와 미정 세부 계약은 별도 검토한다.

2026-10-25 Human의 「여러 조사 결과를 거쳐 우리 로거 스펙을 정해본다면?」 요청에 따른 AI 초안이다. **기존 Human 요구와 ADR-001·003·004를 유지하며, 수치는 설계용 목표로 승인됐다.** 설계/기능 상세의 후보는 별도 검토 사항이고 구현·로컬 성능 검증·의존성 선정은 아직 없다. 0.1은 사양 초안의 표기이며 패키지 버전이나 릴리즈가 아니다.

제품 목표는 대표 로봇 부하에서 제어 주기를 해치지 않고, 선택한 저장·전송·조회·재생 경로로 데이터를 활용 가능하게 만드는 Rust 기반 로깅·텔레메트리 기반이다. RAM 수락 속도와 단계별 지연은 병목 진단에 사용한다.

RT 수집 경로는 초기화 후의 동적 할당·mutex 대기·무제한 재시도·비용이 큰 해제 처리를 피하는 전용 계약을 검토한다. 일반 `tracing`/`log` 호출이나 사용자 정의 포맷/콜백이 같은 RT 계약을 자동으로 만족한다고 보지 않는다. 등록·채널 생성·설정 변경·무거운 해제는 관리 경로로 분리하는 안이다.

제안 메타데이터는 스키마 버전, 세션/채널/생산자 ID, 생산자별 sequence, 단조 시각과 외부 시각의 관계, 이벤트 시각·수집 시각, 로그 레벨, 별도 보존 중요도다. 개별 생산자의 수락 순서는 보존하는 방향을 우선 검토하고, 여러 생산자의 기록은 시각·sequence로 연관 분석한다. 모든 채널의 전역 단일 순서나 서로 다른 PC 시계의 무오차 정렬은 보장 대상으로 가정하지 않는다.

### 12.3 성능 목표 제안

아래 수치는 **AI가 제안하고 Human이 설계 기준선으로 승인한 공학적 초기 목표**다. 공개 자료에서 그대로 확인된 성능이나 dot-logger의 측정 결과가 아니다. 개별 시험 프로필의 부하·기능·하드웨어와 함께 판정하며, 어느 장비에서나 같은 수치를 보장한다는 의미가 아니다. MB/GB는 10진, KiB/MiB/GiB는 2진 단위다.

| 항목 | 초기 목표 제안 | 완료 경계·조건 |
|------|----------------|----------------|
| 동시성 | 32개 생산자 스레드·16개 파일·128개 등록 채널 구성 검증 | 대표 검증 규모. 개수는 설정 가능하며 고정 최대 지원 개수는 아님 |
| 소형 기록 | 합계 100,000 records/s | 1건당 입력 payload 256 B 이하. P1은 파일 쓰기 완료, P3은 최종 영속 동기화 완료도 판정 |
| 대용량 기록 | 합계 1.0 GB/s 이상 | P2/P3, 압축 없음, 인덱스·무결성 검사 활성화, 실제 SSD 기록·종료 배출·최종 동기화 포함 |
| 혼합 부하 | 원본 약1 GB/s와 소형 기록 100,000 records/s 동시 처리 | P3 대표 R1 프로필. 입력과 출력의 실제 payload·메타데이터 bytes를 별도 보고 |
| RT 호출 진단 목표 | p99 ≤5 µs, p99.9 ≤20 µs | 등록·예열 후 전용 RT API, 소형 payload/대용량 핸들 전달. 수락·거절 경로를 각각 측정. 관측 최대값도 보고하며 WCET 보장으로 해석하지 않음 |
| 원격 소형 데이터 | 활용 전달 확인 p99 ≤100 ms | P4, 정상 LAN·소형 기록 10,000/s·클라이언트 1개. 수신 측 디코딩·구독 전달 확인까지, GUI 렌더링 제외 |
| 대용량 원격 전송 | 같은 장비의 TCP 기준 처리량 대비 ≥80% | P4-bulk, 수신 측 레코드 검증·소비 가능 전달까지. SSD 저장은 별도 조합 시험 |
| 조회 | 응답 완료 p95 ≤200 ms | P5, 인덱스 있는 기록에서 소형 데이터 최대1,000건·256 KiB의 한 페이지, 클라이언트1개·초당1회. P3 쓰기와 동시 수행 |
| 관리 메모리 | R1 기준 예산2 GiB 제안. 512 MiB·2 GiB·4 GiB 비교 | 큐·payload 풀·인코딩/압축·송신·재시도·조회 작업 버퍼를 포함하는 예산. 라이브러리 자체 RSS/할당도 추적. OS page cache와 사용자 앱 메모리는 별도 |
| 안정 동작 | 24시간 연속 운전 검증 | 하드웨어별 쓰기/보존 예산에 맞는 선언된 부하, 회전·조회·전송 포함. 상한 없는 메모리/미처리량 증가·교착·설명되지 않는 손상/누락 없음 |
| 제어 영향 | 선언된 정상 프로필에서 기준 실행 대비 로깅으로 추가되는 deadline miss 0회 목표 | 실제 dot-probe 주기·deadline과 동일 부하의 로깅 없는 기준 실행을 함께 기록. OS 설정·부하별 관측 결과이며 보편적 지연 상한 증명 아님 |

1 GB/s와 초당10만 소형 기록은 **동일 기준 장비의 대표 부하 목표**다. 소형 기록은 payload만 약25.6 MB/s를 추가한다. 모든 옵션·DB·압축·클라이언트 수·동시 재생을 이 속도로 무제한 실행한다는 뜻은 아니다. 자원·부하를 고정한 조합마다 판정한다.

Human의 버퍼 증액 의견으로 수정한 R1 기준2 GiB 예산과512 MiB/2 GiB/4 GiB 비교를 설계 기준선으로 승인받았다. 512 MiB는 성능상 필수 상한이 아니며 제품의 고정 최대 용량도 아니었다. 512 MiB·2 GiB·4 GiB 비교 시험을 제안하고, 장비별 설정값과 제품 기본값은 아직 정하지 않는다. 버퍼 용량 조사·계산(비공개 원시 근거: `imported_context/research_2026-10-25_buffer_budget.md`).

배출이 완전히 멈춘1 GB/s 입력에서512 MiB·2 GiB·4 GiB는 각각 약0.54·2.15·4.29초 분량이다. 일부 예산은 작업 버퍼·중요 기록 예약분으로 사용되므로 실제 payload 흡수 시간은 더 짧다. 출력이 일부 유지되면 유입률에서 배출률을 뺀 초과 누적량에 작업·예약·여유 메모리를 더해 산정한다. 버퍼가 저장장치의 지속 부족을 해결한다고 보지 않는다. 중요 기록의 예약 예산·대상별 예산을 비교하고, 초과 시 ADR-003의 관측 가능한 실패·우선 보존 정책을 적용한다. 구체 배분과 중요도 단계는 미정이다.

전체 용량과 I/O 배치 크기·최대 배치 대기시간·실제 미처리량/데이터 나이를 별도 항목으로 둔다. 큰 용량을 채운 뒤에만 배출하지 않으며, 목적별 최신성·지연 목표와 채널별 자원 배분을 함께 평가한다. 작은 핸들 큐와 큰 payload 풀 분리, RT 접근 영역의 시작 전 확보·예열을 우선 검토한다. 정상·버스트·포화 부하에서 지연·CPU·메모리와 로봇 앱/OS에 남는 자원을 확인한다.

소유권 핸들을 보관해 원본의 수명을 연장하는 경우에는 호출자가 할당했더라도 해당 원본의 미처리 bytes를 버퍼 예산에 포함한다. 핸들 크기만 계산해 대기 중인 payload를 예산 밖으로 숨기지 않는다.

### 12.4 기준 장비와 시험 프로필 제안

기준 장비 **R1**의 제안 조건은 x86_64 물리8코어급·RAM16 GiB 이상, Linux + PREEMPT_RT, 동일 파일 시스템/블록·동기화 조건에서 지속 쓰기 기준 처리량 **1.5 GB/s 이상으로 실측된 SSD**다. 제품·커널·파일 시스템·NIC·튜닝은 아직 선정하지 않았고, 구매 요구도 아니다. 1 GB/s급 검증 프로필에 NVMe를 우선 검토하되 제품의 기본 저장 가정은 여전히 SSD이며 SATA 적용을 제외하지 않는다.

원격 시험 R1은 10GbE급 이상이며 두 PC의 TCP 기준 성능을 먼저 측정한다. 선로 속도나 이전의94% 계산값을 실측 기준값으로 사용하지 않는다. CPU pinning·RT 우선순위·할당/해제 정책·worker 수·CPU 사용량·메모리 상한·소켓/블록 크기·MTU를 재현 조건으로 남긴다. 실제 dot-probe 장비가 이 조건과 다르면 별도 프로필에서 실현 가능한 목표를 정한다.

| 프로필 | 입력·구성 | 완료·평가 |
|--------|-----------|-----------|
| P0 기준선 | 같은 장비의 단순 파일 writer·TCP 기준 도구, 로깅 없는 제어 부하 | 같은 bytes·회전·동기화·블록/연결 조건의 기준과 비교. dot-logger의 기능 비용과 하드웨어 병목 구분 |
| P1 소형 | 256 B 이하 기록 합계10만/s. 생산자1/4/8/16/32, 파일1/4/16 | 호출 진단과 파일 완료, 스레드/파일별 지연·공정성. 생성한 모든 레코드의 ID·내용 무결성 확인 |
| P2 원본 | 합성 원본4채널 × 8 MiB ×30/s ≈1.007 GB/s | 소유권 전달부터 실제 SSD 기록과 배출·최종 동기화까지. 실제 센서 사양으로 오인하지 않음 |
| P3 혼합 | P2 + 소형10만/s, 대표32생산자·16파일·128등록채널 | 무손실 정상 부하, 회전·인덱스·체크섬·제어 부하 포함. 편중 분배도 별도 시험 |
| P4 원격 | 소형1만/s·소비자1개, P4-bulk는 큰 payload를 기준 TCP와 비교 | 디코딩·구독 전달 완료를 수신 확인. 송신자의 동일 시계로 잰 확인 왕복시간을 보수적 지연 지표로 사용하거나 동기화 오차를 평가한 별도 일방향 측정 |
| P5 조회 | P3 기록 중 과거 소형 기록1페이지 요청 | 시간·채널 인덱스 조회, 응답 상한·초당1회·클라이언트1개를 고정 |
| P6 장시간/장애 | 24시간·기준 장비별 선언 부하·순환 보존. 느린 파일/구독자·공간 부족·DB/네트워크 단절·프로세스 중단을 별도 주입 | 버퍼/미처리량 상한, 정책별 손실·에러 보고·복구·정상 경로 영향. 전원 차단의 검증은 별도 장비/절차가 필요하며 아직 실행하지 않음 |

수치 목표의 기본 동시 부하는 표에 명시한 조합이다. 예를 들어 P5는 P3와 동시 실행하지만, P4의 최대 전송·P5·압축·DB 출력·재생을 모두 최대 부하로 겹친 성능까지 승인한 것은 아니다. 추가 조합은 부하와 예산을 선언한 별도 프로필로 평가한다.

P3 파일 시험은 예열 후 **60초 이상이며 총 기록량이 RAM의2배 이상**(아래 장시간 기준을 적용하는 장비는 시험 메모리 상한 M의 2배 이상)이 되도록 진행하고, 마지막 미처리 데이터·라이브러리 버퍼·OS 쓰기를 배출해 최종 동기화가 끝날 때까지의 시간을 처리량 계산에 포함한다. 시험 중1초 주기의 동기화 요청을 제안하되 완료 지연을 보고하고 동기화 요청 주기를 전원 장애 손실 상한으로 주장하지 않는다. 파일 생성·회전의 디렉터리 메타데이터 동기화도 필요한 완료 계약에 포함한다.

짧은 SSD 캐시 성능만 채택하지 않도록 기준선의 지속 쓰기와 시간별 처리량·dirty/writeback·동기화 지연을 함께 확인하고 장시간 프로필에서 보완한다. 매개변수별 반복 횟수·통계 방법·도구 버전은 구현 전 검증 계획에서 구체화한다. CPU 사용은 장치별 처리 여유와 함께 판정하며 아직 모든 장치에 공통인 코어 수/사용률 합격선을 정하지 않았다.

하위 성능 장치에는 고정1 GB/s를 강제하지 않는다. 같은 기능과 동기화 조건에서 측정한 기준 경로 대비 **80% 이상의 활용 효율**을 비교 목표로 제안한다. 이80%는 관측된 사실이 아니라 기능 비용에20% 여유를 배정한 초깃값이다. 실제 입력 요구를 처리하지 못하면 비율을 만족해도 그 배포 프로필은 통과하지 못한 것으로 본다.

**장시간 운전 기준(2026-11-08 Human 결정).** 소비자용 SSD는 동적 SLC 캐시가 소진되면 지속 쓰기가 크게 떨어진다(예: 현재 PC Crucial T500 1TB, DRAM 탑재·동적 pSLC 캐시. 같은 계열 2TB 리뷰는 캐시 뒤 약500 MB/s). 로거는 장시간 연속 기록이 본 용도이므로 R1을 만족하지 않는 장비의 P2/P3는 다음으로 판정한다.
- **장비 지속 쓰기 S:** P0 무제한 쓰기로 SLC 캐시를 소진할 때까지 기록하고, 급락 뒤 안정 구간(≥60초) 평균을 S로 둔다. 캠페인 시작 시 측정·기록한다.
- **정상 부하:** P2/P3 제시 속도 = min(1.0 GB/s, **0.6 × S**). 0.6은 효율 목표 0.8의 처리 한계에 다시 25% 여유를 둔 값이다. 무손실·추가 deadline miss 0·주기 sync 기한 안 완료를 요구하며, sync 만료는 실패다. 길이는 예열 뒤 max(60초, 2 × M 분량)이다.
- **효율:** 같은 workload의 무제한(기록량 2 × M) logger ≥ 0.8 × 무제한 P0. 포화가 전제이므로 기록 손실·IO 실패가 없으면 처리량을 인정하고 주기 sync 만료 횟수·지연은 보고한다.
- 캐시 상태에 따른 편향을 줄이도록 P0·logger 순서를 회차마다 교차하고 장비 상태(S, 실행 시각)를 결과와 함께 남긴다.
- **시험 메모리 상한 M·쓰기량 축소(2026-11-09 Human 결정).** SSD 마모를 줄이도록(원안 약 3.5 TiB → 약 0.7 TB) 측정 프로세스를 cgroup `memory.max` = M(기본 8 GiB)으로 실행해 페이지 캐시 흡수를 막고, RAM 2배 대신 2 × M을 쓴다. 정상 부하·효율 행은 1회만 실행하고 효율은 P0·logger·logger·P0(ABBA) 순서로 둔다. 제어·P1 행은 3회, 측정 구간은 60초다. 실행 전에 예상 쓰기량과 대상 드라이브를 알린다.

### 12.5 신뢰성·과부하·복구의 제안

- 정상 P1~P5에서 선언된 예산 이내의 입력은 수락 거절·정책 폐기·손상 없이 완료돼야 한다. 생성 수/bytes, 수락 거절, 대상별 완료·실패·폐기·미처리량을 대조한다. 의도한 중복 출력을 제외한 중복·누락도 검증한다. 폐기를 늘리거나 큐에 쌓아 처리량 목표만 만족시키는 결과는 성공으로 보지 않는다.
- 장애·초과 부하에서는 유한 메모리·RT 무대기·무기한 무손실을 동시에 주장하지 않는다. 중요 기록 우선과 실패 관측 계약을 유지하며 대상별 손실/실패·재시도·지연을 알린다. 중요한 기록까지 포화됐을 때의 반환·예약 규칙은 아직 제안해야 한다.
- 느린 파일·DB·네트워크·구독자가 RT 호출을 대기시키지 않도록 한다. 비정상 대상의 영향 범위를 제한하는 버퍼·작업 예산을 제안하되, 같은 SSD/CPU를 쓰는 정상 대상에 영향이 전혀 없다고 가정하지 않는다.
- 정상 종료는 제한 시간 내 배출·동기화와 미완료/실패 보고를 제공하는 방향이다. 프로세스 중단 시 읽을 수 있는 온전한 구간을 복구하고 손상·미완성 꼬리를 표시한다. 영속 동기화 성공으로 확인한 구간과 단순 수락만 한 구간을 구분한다. 장치/파일 시스템이 동기화 의미를 지키는 조건을 기록하고 전원 장애 무손실은 별도 검증 전 보장하지 않는다.
- 연속·순환·이벤트 구간 기록은 지원하되 보존 기본 모드·기본 디스크 용량·압축·동기화 주기는 이번에 제품 기본값으로 확정하지 않는다. 24시간 운전 시험은24시간 원본 전량 보존 요구가 아니다.

### 12.6 우선 검증할 설계·기술 후보

**모두 미채택 후보**다. 기존 확정 스택을 바꾸지 않으며 의존성·배포 구조를 확정할 때는 ADR 기준으로 승격한다.

- **수집:** 생산자별 고정 용량 큐 + 백그라운드 병합·목적별 분배를 우선 비교. `rtrb`는 SPSC 큐 후보이므로 다중 생산자 전체를 큐 하나에 직접 연결하는 것으로 오해하지 않는다. 큐 자체의 wait-free 특성이 payload 생성·Drop·전체 logger의 보장을 뜻하지 않는다. [공식 rtrb API](https://docs.rs/rtrb/0.4.0/rtrb/).
- **기존 Rust 앱 입력:** `tracing`/`log` 어댑터를 검토하고 전용 RT API와 계약을 구분. `tracing-appender`는 일반 로깅 기준선으로 사용. [tracing](https://docs.rs/tracing/0.1.44/tracing/), [tracing-appender](https://docs.rs/tracing-appender/0.2.5/tracing_appender/non_blocking/index.html).
- **원본/구조화 기록:** MCAP를 우선 검증 후보로 추천. 시간·채널·스키마·인덱스를 갖는 컨테이너와 자체 조회·재생 요구를 비교한다. 자체 형식 전체를 새로 설계하기 전에 성능·복구·인덱스 비용을 확인한다. 사람용 텍스트 출력은 별도 선택 출력 후보다. [MCAP 명세](https://mcap.dev/spec).
- **모니터링/DB:** 네트워크·DB 처리는 RT 밖에서 수행. 수치·이벤트와 센서 원본을 목적에 맞게 분배하고 모든 원본을 시계열 DB에 넣는 구성을 기본 가정하지 않는다. Rust 클라이언트와 기본 점검 CLI를 제안하되 GUI 범위·프로토콜·DB 제품은 후속 결정이다. Prometheus 지표·Grafana 등 연동은 어댑터로 검토하며 외부 서비스 배포를 시작하지 않는다.

ROS 2 호환 검토는 기존 T1(dot-probe 첫 적용 완료) 그대로 유지한다. MCAP 후보 검증은 ROS 2 파일/토픽 호환 구현의 착수를 뜻하지 않는다.

### 12.7 목표의 근거와 남은 결정

- **약1 GB/s:** 센서 용량 시나리오(비공개 원시 근거: `imported_context/research_2026-10-25_sensor_volume.md`)의553~968 MB/s를 첫 검증 규모로 반올림한 공학적 제안. 모든 추가 센서의 총량까지 보장할 여유가 있다는 뜻은 아니다. 공개 MCAP 처리량(비공개 원시 근거: `imported_context/research_2026-10-25_public_benchmarks.md#5-대용량-메시지-기록--mcap와-sqlite-저장-경로`)은 내부 경로의 참고 자료지만 RAM disk·과거 플러그인 수치이므로 SSD 목표의 달성 증거가 아니다.
- **소형10만/s·32스레드·16파일·128채널:** 다수 모터·센서와 동시 로깅 요구에 대응할 대표 시험 규모로 제안했다. 공개 비교에서 그대로 입증된 조합이 아니다. 기록 수와 bytes를 함께 평가한다.
- **호출5/20 µs:** 공개 Rust ns~µs 호출 비용을 참고하고 경합·일반 실행 환경에 대한 여유를 둔 진단 목표다. 평균/중앙값으로부터 p99/p99.9를 도출한 것은 아니며, 실제 전체 호출·정상/실패 경로에서 검증해야 한다.
- **100/200 ms·80%·메모리 예산:** 모니터링 신선도·제한된 조회·기능 오버헤드·메모리 상한을 구체화하려는 초기 예산이다. 메모리는 Human의 증액 검토 의견에 따라512 MiB에서 R1 기준2 GiB 제안 및512 MiB/2 GiB/4 GiB 비교안으로 수정했다. 큰 버퍼가 성능을 위해 작아야 한다는 전제는 두지 않는다. 타 프로젝트가 보장한 값이나 dot-probe가 승인한 SLA가 아니다. TCP/실사용 경로 조사(비공개 원시 근거: `imported_context/research_2026-10-25_end_to_end_tcp.md`), 공개 비교(비공개 원시 근거: `imported_context/research_2026-10-25_public_benchmarks.md`)를 참고한다.
- **영속 완료:** write/flush와 영속 동기화, 파일과 디렉터리의 완료를 구분한다. [Linux fsync/fdatasync](https://man7.org/linux/man-pages/man2/fsync.2.html). 네트워크 기준 도구도 실제 소비 경로와 구분한다. [iperf3 공식 문서](https://software.es.net/iperf/invoking.html).

OQ-002의 정량 목표·R1/P0~P6는 설계 기준선으로 승인됐지만 실제 장비 대응·최종 수락 조건은 미정이며 §15.4의 승인된 보완 계획을 따른다. OQ-003의 중요도/포화·손실·동기화/복구 상세, OQ-004의 배치·클라이언트·DB/프로토콜, OQ-005의 범위·최종 수락 기준은 열려 있다. 여러 정책을 다시 택일하도록 질문하지 않고 기본값·상세 계약을 묶어 제안한다. 다음은 이 사양안을 바탕으로 dot-probe의 실제 검증 장비/제어 부하를 확인하고 프로필과 구현 순서를 구체화하는 일이다.


## 13. 장비별 사용률·처리 여유·잔여 시간 리포트 검토안

### 13.1 기능의 목적과 상태

Human이 실제 사용할 PC 사양과 로그 양·시간 간격을 통해 로거 사용률과 얼마나 더 버틸지 알려주는 리포트를 제안했다. 기존 상태 지표를 활용해 구현 가능한 기능으로 판단한다. **후속 Human 의견으로 운영 중 한계 확인·개발자 로그량 조절 지원을 핵심 가치로 지정했다.** 운영 계측·리포트·간편 점검의 제공 방향은 요구이며, 출력/API·예측 오차·오버헤드 수락 기준과 세부 기능 범위는 아직 미확정이다. 공식 출처·계산·검증 후보 조사(비공개 원시 근거: `imported_context/research_2026-10-25_capacity_reporting.md`).

### 13.2 입력과 기준 처리 능력

- 장비 정보: CPU·코어·RAM·SSD·파일 시스템·NIC·커널과 실제 자원 제한. PC 사양과 제조사 최고 성능은 참고 메타데이터이며 처리 한계의 확정 분모가 아니다.
- 운용 설정: 버전·생산자/채널/파일 수·분배/중복 출력·payload 종류/크기/주기·압축·인덱스·동기화·동시 조회/전송·지연/손실/메모리 예산.
- 실제 관측: 제시 입력·수락·단계별 완료 records/s와 bytes/s, payload/발생 간격 분포, 큐/풀별 점유·순 증가량·가장 오래된 데이터 나이, 단계별 지연, 실패/폐기, 실제 파일 증가/가용 공간, CPU·관리 메모리·OS 자원 경합.
- 기준 처리 능력: 같은 장비·설정·혼합/동시 부하에서 지속 처리량과 지연·자원·손실 기준을 함께 만족한 범위. 원본·압축 후 bytes, 파일 쓰기·영속 동기화 완료, TCP 송신·수신 활용 완료를 구분한다. §12의1 GB/s 목표를 모든 PC의 사용률 분모로 사용하지 않는다.

초기 점검/오프라인 보정 모드와 기존 검증 결과 가져오기를 후보로 둔다. 실행 중인 로봇에 고부하 보정 시험을 자동 실행하지 않는다. 평상시 정상 관측만 있으면 검증된 처리량 하한은 제공할 수 있으나 최대 능력을 확정하지 않는다. 기준이 없으면 해당 사용률은 미측정으로 표시하고 기본 관측만 제공한다.

### 13.3 보고할 값과 의미

| 값 | 계산·표시 방향 | 해석 조건 |
|----|----------------|-----------|
| 단계/대상별 부하율 | 해당 단계 요구량 ÷ 동일 조건의 검증된 용량 | 한계 초과도 표시. CPU 총 사용률·디스크 busy 비율을 logger 전체 사용률로 변환하지 않음 |
| 주요 병목·추가 여유 | 동일 혼합 부하에서 가장 먼저 도달할 한계와 운용 여유 정책을 함께 표시 | 독립 최고값을 동시 능력으로 합산하지 않으며 지연·실패도 판정. 미측정 단계가 있으면 전체 판단의 불완전성을 표시 |

| 출력 정지 시 흡수 시간 | 가용 버퍼 ÷ 현재 유입률 | 실제 포화 예측과 구분한 조건부 시나리오 |

| 연속 기록 잔여 시간 | 실제 사용 가능 공간 ÷ 순 공간 소비율 | 구성 용량 제한·파일 시스템 여유·예약·다른 소비·압축·메타데이터·삭제 반영 |

| 데이터 활용 상태 | 미처리 데이터 나이·지연 기준 초과·실패/폐기와 자원 여유 | 폐기/거절 덕분에 큐 점유가 안정된 경우 정상 여유로 오판하지 않음 |

비율에는 분모·측정 시각·설정/부하 프로필을 표시한다. 추가 가능한 부하는 같은 종류·크기·분배·기능 조합의 증가 범위로 제시하고, 다른 센서를 붙일 때는 그 데이터 크기·발생 주기·처리 비용으로 다시 평가한다. 단일 요약이 있더라도 단계별 값과 미측정 항목·병목 이유를 함께 보여준다.

설정 추천과 부담이 적은 내장 점검의 사용 흐름은 §14에서 추가 상세화한다. 리포트의 실측/추정/미측정 구분과 기준 유효성 규칙은 그 흐름에도 그대로 적용한다.

### 13.4 추정 품질·출력·실행 비용

측정값, 측정 기반 추정, 미측정/조건 불일치, 만료된 기준을 구분한다. 관측 구간·변동과 가정을 함께 표시하며 장비/옵션/부하 변화 시 기준의 유효성을 재평가한다. 현재 추세에서 증가하지 않는다는 결과를 무기한 안전으로 표현하지 않는다. 예측 시간은 해당 자원/정책 한계까지의 조건부 값이며 장비의 고장 수명을 추정하는 계약은 아니다.

1초 수집·10/60/300초 추세 집계는 초기 후보다. RT 경로에서는 제한된 카운터/시각 기록만 검토하고 수집·계산·파일/JSON 출력은 백그라운드에서 수행한다. 채널/레이블 수·통계 이력·질의·출력 비용을 제한하고 리포트 자체의 CPU·메모리·호출 지연 영향을 측정한다. 초기 출력 후보는 Rust 보고서 API·CLI·JSON, 외부 전달 후보는 기존 모니터링/Prometheus 연동이다. 이를 위해 Prometheus/Grafana 설치를 필수화하거나 별도 화면 범위를 확정하지 않는다.

단계/계단/버스트 입력, 출력 정지/회복, 압축률·목적별 편중·중복 출력·순환 보존 변화, counter reset·결측·기준 만료, 의도적 폐기 상황에서 실제 한계 도달과 추정·경고 시점을 대조한다. 예측 오차·오경보·경고 선행시간·관측 오버헤드의 합격선은 후속 설계/검증에서 제안한다. 리포트가 설정을 자동 변경하거나 부하를 자동 제한하는 기능은 이번 아이디어에 포함한 것으로 간주하지 않는다.


### 13.5 핵심 강점과 개발자 조절 지원

Human이 운영 중 한계 확인과 개발자의 로그량 조절을 dot-logger의 강점으로 지정했다. 개발자가 별도 측정 작업을 매번 준비하지 않고 **사용 중 관측 → 병목/여유 확인 → 기록량 조절 → 변경 효과 재확인**을 수행할 수 있게 하는 방향이다. 별도 점검은 측정된 범위를 넓힐 필요가 있을 때 연결한다. 핵심 방향은 확정이며 아래 상세화의 API·설정·판정 기준은 후속 설계다.

- **조절할 위치를 찾는 정보:** 채널·생산자·장치·출력별 records/s·bytes/s·크기/간격/버스트, 처리 비용·완료량·지연·미처리량·실패/폐기를 제공하는 안이다. 측정 가능한 범위를 표시하고 비용의 단순 비례 합산이나 단일 전체 사용률만으로 판단하지 않는다.
- **개발자가 선택할 조절 수단:** 기록 레벨/필터, 채널별 기록 주기·샘플링, 원본/필드 선택·요약, 파일/DB/네트워크 출력 대상을 조절하는 인터페이스와 사용 예시를 설계한다. 요약은 개발자가 만든 데이터의 입력도 포함하며 logger가 모든 센서 변환을 내장한다는 뜻은 아니다. 센서 자체의 제어/수집 주기와 기록 주기를 구분한다.
- **조절 비용·정보 손실의 설명:** 추천에는 절감할 입력/출력/자원과 잃는 기록 범위·시간 해상도·복구/분석 영향을 함께 표시한다. 로그 레벨과 별도 보존 중요도 계약은 유지하며 개발자의 선택 없이 중요 기록을 자동으로 줄이는 동작은 가정하지 않는다.
- **변경 전후 확인:** 설정 버전·장비·옵션·관측 구간·애플리케이션 부하를 연결해 같은 조건의 기록량·완료량·지연·메모리·순 증가량·보존 시간 변화를 비교하고 결과를 남긴다. 설정에 의한 의도적 생략, 수락 거절, 포화 폐기, 저장/전송 실패를 각각 구분한다. 비교 조건이 다르면 그 차이를 표시한다.
- **비용이 줄어드는 지점의 구분:** 출력 단계에서만 필터링한 효과와 생산자가 비용이 큰 payload 생성/인코딩 전에 기록 여부를 판단해 줄인 효과를 구분한다. 로거의 조절이 앱의 센서 취득·영상 처리 비용까지 자동으로 줄였다고 보고하지 않는다.
- **사용 중 계측의 부담:** 일상 관측은 제품 사용 흐름에 포함하고 별도 벤치마크를 실행해야만 정보를 얻는 구성으로 만들지 않는 방향이다. 상세 계측 수준·주기·기본값은 실행 비용과 함께 설계하며 RT 경로의 제한된 작업·관리 메모리 예산과 실제 소비 경로의 검증 조건을 유지한다.

성공 여부는 처리량 외에 사용자가 실제 주요 부하 원인을 찾고 조절 후 변화·의도한 생략·예상치 못한 손실을 구분해 확인할 수 있는지로 평가한다. 대표 시나리오는 센서 원본 기록 빈도 감소, 디버그 기록 필터 변경, 수치 채널의 샘플링 변경, 출력 대상 조정 전후 비교다. 설명용 시나리오를 자동 실행/자동 제한 기능 승인으로 취급하지 않는다.


## 14. 질문 프리셋·설정 추천·간편 점검 검토안

### 14.1 사용자 문제와 상태

Human은 질문 프리셋으로 PC 성능에 따른 기본 설정값을 추천하고, 사용 중 처리 가능 여부를 쉽게 측정할 수 있기를 원한다. 별도 측정 도구·부하 모델·명령·해석을 직접 준비해야 하면 측정을 잘 하지 않게 되는 문제가 있다. §13의 리포트에 **시작 설정 추천 → 일상 관측 → 한 번의 실행으로 점검 → 해석과 설정 제안**을 연결하는 제품 기능 제안이다. 구현·CLI 명령·프리셋 이름·점검 시간·추천 수치·우선순위는 미확정이다.

### 14.2 처음 사용할 때의 설정 추천

장비의 CPU·메모리/자원 제한·SSD/가용 공간·NIC·OS와 현재 로거 설정을 자동 확인하는 안이다. 자동으로 확인할 수 있는 값을 다시 묻지 않고, 알 수 없는 사용 의도만 짧게 확인한다. 질문은 한 번에 하나씩 진행하고 불확실하면 모름/일단 관측 후 제안 경로를 둔다.

질문 예시는 무엇을 기록하는지(상태 로그/수치/센서 원본 혼합), 얼마나 과거 데이터를 남기려는지 또는 사용할 디스크 예산, 로봇 운전 중인지/별도 점검 가능한 환경인지다. 이는 제품 안내 예시이며 현재 프로젝트의 정책 지원을 다시 택일하도록 묻는 것이 아니다. 예상 데이터량·발생 간격을 모르면 실제 관측으로 채우고, 초기 선택은 이후 수정할 수 있도록 한다.

용도 프리셋은 상태 로그 중심·로그+수치·센서 원본 혼합 등의 후보를 제공하고 장비별로 버퍼/풀 예산·worker 수·파일 배치·최대 배치 대기시간·회전/보존/동기화 설정을 추천하는 안이다. 각 추천에는 현재 장비에서의 가정·사용 메모리/디스크·예상 효과·보존/지연 영향·확인되지 않은 부분을 표시한다. 임의의 RAM 비율만으로 처리 능력을 검증했다고 주장하지 않는다.

현재 설정을 읽어 변경점과 이유가 있는 설정 초안을 생성하고, 사용자가 선택해 적용·저장할 수 있게 한다. 실제 적용은 명시적 동작으로 수행하고, 기존 설정은 보존해 되돌릴 수 있도록 하는 안이다. 사용자 고정값과 ADR-003의 RT 무대기 계약을 추천이 조용히 덮어쓰지 않는다. 기본 모드/중요도/용량/주기는 아직 별도 선정 사항이다.

### 14.3 사용 중 관측과 내장 점검

| 방식 | 사용자가 하는 일 | 제품이 수행할 일 | 결과의 의미 |
|------|------------------|-----------------|-------------|
| 일상 관측 | 로거 사용과 관측 기능 설정 | §13의 제한된 계측으로 실제 크기·간격·버스트·목적별 출력·지연·자원/미처리량 추세를 누적 | 관측한 부하의 처리 여부·검증된 하한. 최대 처리 능력 확정은 아님 |
| 간편 점검 | 선택한 점검 환경에서 한 번 실행 | 관측한 부하 프로필을 가져와 현재/증가 부하를 재현하고 저장·동기화·선택 전송 경로를 측정, 결과와 추천을 저장 | 지정 시간/데이터량·구성에서 실제 검증한 범위. 짧은 시험은 단기 결과로 표시 |
| 지속·상세 시험 | 필요할 때 더 긴 점검 선택 | 같은 프로필로 SSD 캐시 이후·긴 burst·동시 부하·반복 회전 등을 더 오래 시험 | 관측한 지속 조건의 검증 범위. 24시간 시험과 같다고 간주하지 않음 |
| 추가 부하 시나리오 | 채널/센서·빈도·크기 또는 현재 부하의 증가량 입력 | 측정한 같은 조건의 범위와 비교해 추정하고 선택 시 재현 점검으로 확인 | 모델 추정과 실제 재현 검증 결과를 구분 |

소형 로그 수·시간 간격·payload 크기·생산자/파일 수·출력 비중 등 실제 로깅 부하 프로필을 가능한 한 자동 생성하여 사용자가 부하 스크립트를 작성하지 않게 한다. 관측 메타데이터만으로 원본의 내용·압축률·상관관계를 정확히 재현할 수 없으므로 합성/실제 데이터·압축/인덱스·내용 차이를 결과에 명시하고 필요한 경우 대표 데이터를 선택하는 경로를 제공한다. 센서 종류/기능 조합이 바뀌면 같은 모델이 유효하다고 가정하지 않는다.

간편 점검의 수십 초 수준 실행은 사용성 목표 후보이며 정확한 시간·총 쓰기량·부하 단계는 미정이다. 점검 전에 예상 시간·CPU/메모리·쓰기량/공간·전송량을 준비된 기본값으로 제시하고 필요 시 바꿀 수 있게 한다. 사용자가 현재 운전 중인 경우 평상시 관측을 우선 제안하며, 고부하 시험은 별도 점검 환경/시간에서 명시적으로 실행한다.

점검은 자체 임시 파일/정해진 대상만 사용하고 기존 운용 기록을 덮어쓰지 않으며, 시간·기록량·공간·부하 예산과 취소/중단 조건을 적용한다. 종료 시 버퍼 배출·동기화·최종 집계와 성공/미완료/중단 구분, 생성한 임시 자원의 정리를 포함한다. 네트워크 경로는 실제 수신자/점검 상대가 없으면 미측정으로 남기고 localhost/RAM 성능으로 대체해 원격 성능을 인증하지 않는다.

### 14.4 결과와 추천의 표현

결과는 관측 범위에서 처리 가능, 지정 추가 부하까지 점검 통과, 미처리량/지연 증가, 특정 경로의 검증 부족 등으로 구체적으로 표현한다. 현재 PC의 최대 능력을 측정하지 않았으면 최대 대비 비율은 미측정으로 유지한다. 예를 들어 같은 부하의1.3배를60초 동안 재현해 통과했다는 결과는 그 조건의 검증 증거이며 지속 운전 한계의 확정값이 아니다. 수치는 설명 예시일 뿐 정해진 점검 기본값이 아니다.

현재 설정과 추천 설정의 차이·추천 이유·메모리/디스크/지연/보존 영향·측정 근거·이전 결과 대비 변화·다음에 확인할 항목을 같이 제시한다. 결과와 장비/설정/부하 프로필을 재사용 가능한 기록으로 남겨 같은 질문·시험 준비를 반복하지 않도록 한다. 변경된 장비/옵션/부하의 기준 유효성은 §13에 따라 재평가한다.

추천은 사용자가 적용할 설정 초안이다. 자동 샘플링·중요도 변경·삭제/보존 정책 변경·운영 중 재시작을 이번 기능의 기본 동작으로 포함하지 않는다. 내장 점검 도구가 별도로 제공돼야 한다는 구현 방향은 제안 상태이며 GUI/CLI/Rust API의 최종 범위도 후속 선정한다.

### 14.5 검증할 사항

알 수 없는 장비/제한된 권한/컨테이너 자원 제한, 데이터량을 모르는 사용자, 기존 사용자 설정 유지, 설정 초안 검증/재사용/되돌리기, 점검 취소·오류·공간 부족·상대 수신자 없음·프로필 변경·짧은 SSD 캐시 착시를 검증 후보로 둔다. 추천 정확도·질문 수·완료 시간·계측/점검 비용·중단 동작의 수락 기준은 아직 정하지 않았다. 구현 착수 전 실제 사용 경로와 단계별 범위를 구체화한다.


## 15. 설계 진입 준비 점검과 기준선 검토

### 15.1 현재 결론과 검토 범위

**전환 확정: 2026-10-25 Human 「확정」, ADR-005. Gate 1·2 Pass(승인된 설계 이월 포함), 현재 Phase Design.** 이 절은 이전 준비 점검과 후속 승인 결과를 함께 보존한다.

2026-10-25 Human이 목표/성능 목표의 정립 수준과 다음 단계 진입 가능 여부를 확인했다. **프로젝트 목표·핵심 가치·Must 기능 방향은 정리됐으며 설계 입력으로 사용할 기능/성능 초안이 있다.** 후속 Human 「확정」으로 초기 수치의 설계 기준선·Story/AC·미결 보완·산출물 계획을 승인받았다. 개별 장비의 성능 달성·최종 SLA·미검토 기술 채택으로 기록하지 않는다.

프로젝트 목표 승인은 Human이 직접 지정한 내용에 따라 Intent와 인덱스에 반영했다. Pre-Gate Harvest로 기능 명세·용어집·US-001~004/수락 기준 초안을 보충하고 산출물 계획의 구체안을 작성했다. 이번 확정으로 이 준비 내용과 보완 계획을 설계 기준선으로 사용한다. 향후 모든 상세 설계나 성능 보장의 승인을 뜻하지는 않는다.

### 15.2 범위·비목표·우선순위

- **핵심 범위:** Rust·Linux/macOS/Windows 재사용 라이브러리와 클라이언트, Linux PREEMPT_RT 실시간 프로필, 다중 생산자/목적별 다중 파일, 로그/수치/원본 기록, 파일 관리·시계열 DB 연동·자체 조회/재생·모니터링, 운영 계측·리포트·간편 점검·개발자 조절과 전후 효과 확인. FR-001~014·016·017과 후속 추가 FR-018(전원 이상 시 중요 파일 우선 기록)은 Must 방향이다.
- **추가 제안:** FR-015 질문 프리셋·장비별 시작 설정 추천의 세부 범위·우선순위는 검토 대상으로 남는다. 핵심 관측/점검 지원의 필요성과 구체 UI/편의 기능은 구분한다.
- **기존 범위 밖/비보장:** ROS 2 파일·토픽 호환은 dot-probe 첫 적용 후 T1.24시간 원본 전량 보존은 요구가 아니며 모든 장비/기능 조합에서 무제한 무손실·고정 지연·동일 처리량을 보장하지 않는다. 모든 원본을 시계열 DB로 보내는 구성을 강제하지 않는다.
- **첫 설계에서 제외할 제안:** 캐릭터 UI/독자 GUI를 필수로 정하거나 개발자 선택 없이 로그를 자동 감축·재설정하는 기능은 기본 범위에 추가하지 않는 안이다. Rust 보고서 API/CLI 등 구체 제공 형태는 설계에서 제안한다. 이는 기존 Must 모니터링 기능을 없애는 의미가 아니다.

### 15.3 성능 기준선의 검토안

[§12](#12-초기-통합-사양안--제안-01)를 **설계용 초기 목표**로 검토한다. 핵심 값은 원본1 GB/s급 + 소형10만건/s 혼합,32생산자·16파일·128채널 검증, R1 관리 버퍼2 GiB와512 MiB/2 GiB/4 GiB 비교, RT 호출 p99 5 µs/p99.9 20 µs 진단 목표, 소형 원격 전달 p99 100 ms, 제한된 조회 p95 200 ms, 기준 TCP 대비80% 전송,24시간 운영이다. 완료 경계·장비·동시 부하 조건은 §12의 표/프로필을 따른다.

이 기준선은 하드웨어/알고리즘·비용을 검토하고 이후 시험으로 확인할 목표다. 장비 실측·압축·부하·동기화·모니터링 형태가 달라지면 조건과 수치 변경을 함께 검토한다. 버퍼2 GiB나1 GB/s가 모든 사용 환경의 고정 기본값·실측 용량·보장 SLA가 되는 것은 아니다. 최종 합격 판정은 유효한 장비/프로필의 검증 근거에 따른다.

## 16. 크로스 플랫폼 지원과 검증 범위

2026-10-25 Human 지정(ADR-006) 및 후속 합의에 따라 Linux·macOS·Windows 지원을 필수 요구로 하되, 플랫폼 역할을 **Tier 1 (Target / Full SLA)**과 **Tier 2 (Compatibility / Best-Effort)**로 명확히 계층화한다. 이를 통해 실제 로봇 RTOS 환경의 엄격한 성능 보장과 개발자 워크스테이션(Mac/Windows)의 개발·분석 편의성을 양립시키고 불필요한 OS별 튜닝 오버엔지니어링 및 CI 불안정성을 방지한다.

| 구분 | **Tier 1: Linux (PREEMPT_RT / 일반)** | **Tier 2: Windows, macOS** |
|------|--------------------------------------|---------------------------|
| 역할과 용도 | 실제 로봇 탑재(IPC), 실시간 제어 루프 연동 | 로컬 개발, 시뮬레이션, 로그 재생/분석, 모니터링 클라이언트 |
| 기능 지원 | 전체 수집·기록·보존·조회·계측 API 100% 보장 | 전체 API 및 기능 100% 호환 제공 |
| 성능 측정·SLA | • RT 호출 지연 진단 목표 (p99 ≤5 µs, p99.9 ≤20 µs)<br>• 1.0 GB/s + 소형 10만/s 혼합 처리량<br>• UPS 약3초 전체 예산 내 긴급 동기화 목표 (FR-018, 활성 장비별 실측 필요) | • **성능 측정 및 엄격한 RT SLA 대상에서 제외 (Best-Effort)**<br>• OS 스케줄러 환경에 따른 일반 파일/데이터 처리 성능 위주 |
| 자원 및 코어 격리 | 백그라운드 I/O 워커의 **CPU 코어 격리(Affinity/Pinning)** 및 우선순위 지정 지원 (`sched_setaffinity`) | OS 지원 범위에 따라 선택적 적용 (미지원 시 capability 결과를 표시하고 기본 스케줄러 사용; required 요청은 명시 실패) |
| 검증 범위 | 네이티브 실시간 부하 시험 (P0~P6) 및 하드웨어 실측 검증 | 기능 단위/통합 테스트, Linux 생성 로그의 상호 읽기/재생(Interoperability) 검증 |

지원 선언은 아직 실행 검증 결과가 아니다. OS별 세부 버전·CPU 아키텍처·MSRV·의존성/기능 지원·네이티브 빌드/시험/배포 매트릭스는 Design에서 정한다. R1/P0~P6와 초기 목표는 Linux PREEMPT_RT 참조 프로필로 유지하며 macOS/Windows에 같은 수치를 자동 적용하지 않는다. API의 무대기 동작 계약과 전체 OS 스케줄링을 포함한 지연 검증을 구분한다.

공통 경로와 OS별 시각·스레드/우선순위·파일/영속 동기화·회전·자원 관측을 분리해 설계한다. Linux 전용 자원 지표가 없거나 권한/기능이 미지원이면 미측정/미지원으로 표시하고0 또는 정상으로 추정하지 않는다. 핵심 관측·리포트가 Linux 전용 지표에 필수 의존하지 않도록 한다.

공통 기능의 실제 실행, 파일 생성/회전/재열기/중단 복구·완료 의미, 시간·순서, 동시 기록, 플랫폼 간 기록 읽기, 리포트/점검과 지표 부재를 OS별로 검증한다. 크로스 컴파일 성공만으로 기능/성능 통과를 판정하지 않는다. 구체 시험 비용·절차는 후속 검증 계획으로 형성한다.

## 17. 전원 이상 시 중요 파일 우선 긴급 기록

### 17.1 요구와 시간 기준

FR-018은 2026-10-25 Human의 기능 추가 요청이며, **UPS 신호 발생 → 실제 전원 차단의 전체 시간이 약 3초**임을 확인했다. 전원 차단 전에 사전 지정한 중요 파일의 미기록 내용을 우선 저장하는 기능을 제공한다. 중요 파일 목록/순위는 설정 가능하게 설계하고, 개별 기록의 보존 중요도·로그 레벨과 파일의 긴급 저장 우선순위를 구분한다.

**사용 정책 확정: 선택적으로 활성화하는 옵션이며 기본값은 비활성이다.** 제품의 옵션 제공 요구(Must)와 각 배포의 활성화 여부를 구분한다. 비활성 상태에서는 이 기능에 의한 긴급 저장 전환·전용 자원 예약을 하지 않고 일반 기록/종료 계약을 유지한다. 활성화할 때 중요 파일 계획·신호 연동·예산을 검증하는 안이다. 아래 약 3초 조건과 긴급 동작/검증은 활성화한 구성에 적용한다. 실행 중 활성화/비활성화 변경 범위와 빌드 기능 분리는 아직 미정이다.

기능 방향과 전체 약 3초 조건은 Human 확인 사항이다. 아래 완료 경계·동작·수락 기준은 상세 검토안이며 장비/OS별 시간 보장이나 앞선 API 권고안의 채택을 뜻하지 않는다.

```text
신호 발생부터 차단까지의 시간 ≈ 3초
로거 가용 예산 = 전체 예고 시간 - 신호 전달/감지 지연 - 종료/전원 차단 안전 여유
중요 범위의 기록·필수 메타데이터·영속 동기화 소요시간 ≤ 로거 가용 예산
```

약 3초를 로거의 신호 수신 뒤 새로 시작하는 타임아웃으로 쓰지 않는다. 신호 발생 시각/차단 기한을 직접 알 수 없으면 검증한 전달 지연 상한으로 남은 예산을 보수적으로 계산한다. 상한도 모르면 시간 충족은 미검증으로 표시한다. 실제 UPS 유지시간의 편차, 호스트와 SSD/컨트롤러의 전원 유지 조건은 해당 장비 프로필에서 확인한다.

### 17.2 기능 동작 검토안

1. UPS/전원 관리 어댑터가 전원 이상과 남은 기한을 관리 경로에 알린다. 장치/프로토콜은 미선정이며 RT 생산자/OS 비동기 신호 핸들러 안에서 파일 IO를 실행하지 않는다.
2. 미리 검증한 긴급 저장 계획을 적용한다. 중요 파일 순위·보호할 기록 범위·최대 미동기화 bytes·필요 메타데이터/복구 단위를 정하고, 신규 일반 입력·비필수 출력/조회는 사전 설정한 긴급 정책에 따라 제한하는 안이다. 마지막 상태를 추가 수락한다면 별도 제한 예산과 최종 마감 범위를 둔다.
3. 중요 파일부터 쓰기·영속 동기화를 수행하고 남은 시간에 다음 순위 파일을 처리한다. 파일명/회전·인덱스 등이 복구에 필요하면 해당 범위도 포함한다. DB·네트워크 응답이나 전체 일반 원본 배출을 중요 로컬 파일 완료의 선행 조건으로 두지 않는 방향을 검토한다.
4. 파일별 완료·실패·미완료와 기한 초과를 구분한다. 결과 자체도 저장 여유 안에서 남길 수 있을 때 기록하며, 전원이 끊긴 뒤 미기록 결과까지 보고됐다고 가정하지 않는다. 재기동 때 실제 복구 범위를 대조한다.

전원 이상 대응은 명시적으로 구성된 비상 정책이다. 일상 운영의 자동 기록량 조절 기본값을 바꾸지 않는다. 이미 실행 중인 큰 쓰기/동기화를 즉시 선점·취소할 수 있다고 가정하지 않으며 파일별 처리 단위·미동기화량을 평소부터 제한하는 설계를 비교한다. 임의 크기의 전체 버퍼를 약 3초 안에 무손실 저장한다고 약속하지 않는다.

### 17.3 미결과 검증 계획

- **OQ-002:** 실제 UPS 신호/유지시간·전달 지연·SSD/파일 시스템·공유 IO 부하에서 중요 파일의 보호량과 소요시간을 확인한다.
- **OQ-003:** 중요 파일 순위·동일 순위 처리·정상/긴급 기록 중요도 관계·신규 입력 마감·동기화/복구 단위·실패/시간 초과 정책을 핵심 저장 계약 전에 합의한다.
- **OQ-004·005:** OS별 어댑터·신호 전달과 종료 연동, 전체 시간 계측·안전 여유·장비별 수락 기준을 해당 구현 전에 정한다. UPS 제어 소프트웨어나 하드웨어를 현재 채택하지 않는다.

추가 수락 기준 초안은 [US-002](user_stories/US-002_retention_and_recovery.md)에 둔다. 우선순위가 다른 여러 파일, 큰 일반 쓰기 진행 중 신호, 최대 보호 미처리량, 신호 지연/중복/지연 도착, 디스크 오류/포화, 실제 전원 차단 후 재기동·파일/내용/복구 경계를 확인한다. 각 지원 OS/UPS/SSD 조합에서 신호 발생부터 계측하고 전체 약 3초 조건의 지원 여부를 판정한다. 소프트웨어 모의 신호만으로 전원 차단 내구성을 검증했다고 표시하지 않는다.

## 18. 상세설계·실행 계획과 추적

2026-10-26 진행현황 점검 후 상세설계를 시작했다. Human이 **Rust 클라이언트 API + CLI·dot-probe 기존 화면 연동**과 **내장형 Ports and Adapters + 제한된 백그라운드 파이프라인(ADR-007)**을 선택했다. 이전 절의 클라이언트/실행 구조 미정 표현은 해당 선택 범위에서 해소됐다. 후속 Human 「권고 기준선 채택 — 장비·호환 검증은 계획대로 진행」으로 ADR-008·009·상세설계·추가 AC·MS 계획을 승인받았다. Gate 3 Pass, 제품 구현/실측은 미완료다.

- 설계: [도메인](../03_design_artifacts/domain_model.md), [데이터](../03_design_artifacts/data_model.md), [API](../03_design_artifacts/interface_contract.md), [CLI](../03_design_artifacts/ui_spec.md).
- 구현 계획: INT-001 → [MS-001~007](../04_implementation/milestone_registry.md) → [Task 목록](../04_implementation/task_registry.md). Gate 3 Pass(2026-10-26), 다음 구현 진입점 TASK-002.
- 체크리스트: [요구사항–설계–구현–테스트 추적표](../05_verification/test_case.md#3-요구사항설계구현테스트-추적-체크리스트). MS별 구현/테스트를 각각 체크하며 EV/코드 근거를 연결한다.
- 공식 자료와 dot-probe 조사(비공개 원시 근거: `imported_context/research_2026-10-26_detailed_design.md`): 기존 후보를 독립 검토. 문서 확인을 제품 성능 시험으로 표시하지 않는다.

2026-10-31 Human 승인으로 실제 장치 시험은 **현재 Ubuntu PC 실측으로 대체**한다(ADR-011·§19). 이전 잘못된 확정 클릭 정정 이력 뒤 새로 확정한 결정이다. R1은 참조 조건이며 PC 환경·제어 부하/기한은 TASK-022에 기록하고 UPS는 시뮬레이션으로 판정한다. 보장 문구는 기존 §12/ADR-005의 조건부 목표로 읽으며 affinity·내장 프로세스만으로 완전 격리·보편적인 SLA를 선언하지 않는다. Tier 1/2 지원 방향은 변경하지 않는다.

### 상세설계 승인 후 미결의 해석

이전 절의 미정/제안 문구 중 ADR-008·009 및 인터페이스 §13~17에서 구체화한 계약·기술은 승인된 현재 기준으로 대체한다. OQ-003의 계약 선택은 해소됐고, 실제 수명/알고리즘 증명·장비별 보호량/손실 수치는 구현/실물 검증에 남는다. OQ-004의 기술 선택은 해소됐으며 patch/MSRV 호환 검증은 TASK-002다. OQ-005의 계측·점검·변경 계약/시험 목표는 승인됐고 FR-015는 계속 별도 제안이다. OQ-002의 검증 PC/UPS 수락 방식은 ADR-011·§19로 확정했으며 제어 부하/수치 프로필은 TASK-022에서 구체화한다.

## 19. 검증 환경·수락 방법 변경 — 2026-10-31

Human의 명시적 결정([ADR-011](../03_design_artifacts/adrs/ADR-011_local_pc_simulated_ups_verification.md))으로 §12·15~18과 FR-018/US-002 AC-7~9의 시험 방법을 다음과 같이 갱신한다. 동작/예산 목표는 유지하고 시험 방법은 이 절을 우선한다.

- 실제 장치 시험은 현재 Ubuntu PC에서 수행한 IO/동기화/복구·재생/성능/자원 실측으로 대체 수락한다. 별도 로봇/센서/UPS 장비 제공을 필수 입력으로 요구하지 않는다. dot-probe 소프트웨어 통합 범위는 유지한다.
- UPS 실물 제공/전원 차단 시험은 필수 수락에서 제외하고 모의 신호→전달 지연/안전 여유→전체 약3초의 모의 차단 기한→실제 파일 sync 및 중단/재개/복구 대조 시뮬레이션으로 판정한다. 물리 전원 차단 내구성의 관측 증거와 구분해 '시뮬레이션 수락'으로 보고한다.
- GitHub native 검증은 공개 완료 후 재개하는 승인된 이월이다. 공개 전 구현/로컬 검증을 진행하며 GAP-004 Not Run과 다른 OS 미검증 범위를 보존한다. 공개 전 라이선스/운영정책/이력 검토(T2) 후, 공개 완료 확인 시 source hash를 고정해 native 검증(T3)을 수행한다.
- 현재 실행 커널은 일반 `7.0.0-42-generic`, 설치된 RT 커널은 `7.0.0-38-realtime`(CONFIG_PREEMPT_RT=y)이다. 실행 근거는 부팅한 커널별로 구분한다. 제어 주기/deadline·부하·P0 기준선·저장 예산은 TASK-022에서 선언하고 실행 결과로 목표 충족을 판단한다.

이는 시험 실행 결과가 아니며 아직 미실행인 측정/모의 시나리오를 Pass로 바꾸지 않는다.
