# INT-002 — AI가 로그와 소스코드로 애플리케이션 자기개선을 돕는 분석 도구 (아이디어)

## 상태

`Draft` — 2026-11-21 Human 아이디어 제시. 목표·범위·우선순위는 정하지 않았다. 이 문서는 논의 기록이며 승인된 요구가 아니다. INT-001 마무리(Gate 4·5, TASK-024·026) 뒤에 이어서 구체화한다.

## 출발점 — 2026-11-21 논의

- **로거의 두 역할(Human):** 첫째는 애플리케이션이 기록하려는 것을 신뢰성 있고 빠르고 안전하게 기록하는 것이고, 둘째는 그 데이터를 활용하기 쉽게 해 주는 것이다. INT-001은 첫째에 집중했고, 사건 전후 보존·조회·재생·전후 비교처럼 둘째의 기반도 일부 갖췄다.
- **로그를 쓰는 목적:** 문제가 생겼을 때 원인을 찾아 고치고, 수치를 보고 기능을 개선한다. 로보틱스에서는 기록을 재생해 회귀를 확인하고, 튜닝·학습 데이터로도 쓴다.
- **로거의 한계와 AI:** 로거는 기록의 도메인과 의미를 몰라 내용 분석을 할 수 없다. AI는 로그 내용과 그 로그를 남긴 소스코드를 함께 읽을 수 있으므로 오류 분석과 기능 개선을 도울 수 있다.
- **실제 사례(dot-probe):** 로봇 300대의 실시간 정보를 Redis(큰 메모리)에 넣고 분석해 소스 수정 → 시험 → 분석 → 수정의 자기개선 사이클에 들어가 있다.

## 아이디어 (Human)

`.agent`·`.cowork`·`.logger`처럼 **다른 애플리케이션 폴더 안에 사는 구성 요소**를 만든다. AI가 그 애플리케이션의 로그와 소스코드에 접근해 자기개선을 돕는다.

- 로그를 보고 코드 개선을 제안한다.
- 원인을 가리는 데 필요한 로그가 없으면 추가할 기록 지점을 제안한다.

## AI 검토 의견 (2026-11-21, 결정 아님)

dot-logger가 이 일에 유리한 이유는 **기록과 코드를 정확하게 이어 주는 일은 기록을 만든 쪽이 가장 잘할 수 있기** 때문이다. 이미 있는 재료는 다음과 같다.

- 스키마·채널·writer 등록(각 기록이 어떤 타입이고 어디서 왔는지)
- 설정 revision과 전후 비교(수정 → 재실행 → 효과 확인 루프의 기반)
- 손실 카운터(데이터가 빠진 구간을 정상으로 오해하지 않게 하는 근거)
- 사건 전후 보존, 조회·재생, `.logger/` 폴더 관례

성패를 가를 설계 포인트는 다음과 같다.

1. **AI에게 원본을 통째로 주지 않는다.** AI 질문에 필요한 구간만 요약해 돌려주는 조회 계층이 필요하다. 예: 오류 전후 N초, 수치 분포와 이상 구간, revision 간 차이. MCP 서버나 JSON CLI 형태가 후보다.
2. **기록 ↔ 코드 연결.** 기록이 나온 코드 위치와 빌드 커밋이 남아야 AI가 다른 버전의 코드와 로그를 맞춰 보지 않는다. 지금은 tracing 호출 위치와 설정 revision만 있고 빌드 커밋 등은 추가가 필요하다.
3. **"정상"에 대한 지식.** 채널의 의미·단위·정상 범위·불변 조건을 적은 명세 파일을 `.logger/`에 둔다. 사람이 시작하고 AI가 보강한다.
4. **로그 추가 제안**은 기존 관측 도구에 거의 없는 독자적 강점이 될 수 있다.
5. **사람 승인.** AI는 패치를 제안하고, 시험과 전후 비교를 통과한 뒤 사람이 승인해 반영한다. 로봇은 물리적으로 동작하므로 필수다.
6. **민감 정보.** 기본은 로컬 처리로 하고, 외부로 내보낼 범위는 명시한다.

구조 의견: 로거 core는 도메인을 모르는 범용 라이브러리로 유지하고, AI 분석 계층은 선택적인 별도 구성 요소(별도 crate·도구 또는 별도 저장소)로 둔다. 성격이 다르므로 INT-001에 붙이지 않고 INT-002로 연다(Human 「INT-002로 하고싶다」).
