- 목표: dot-logger가 RT 로거(NanoLog·Quill·LTTng·defmt 등)와 같은 기준으로 비교될 수 있게 수집 비용을 공개하고, RT 스레드에서 쓸 글줄 경로와 기록 타입 정의 부담을 줄여 외부 사용자가 받아들이기 쉽게 한다.

## 배경 — 외부 관점 지적(2026-11-23)

| # | 지적 | 확인한 현재 상태 |
|---|---|---|
| 1 | RT 수집 비용이 숫자로 없다. README 측정은 gRPC 확인 지연·처리량뿐. RT 로거 비교에는 `try_log` 한 번의 지연 분포(PREEMPT_RT p50·p99·최대, 캐시가 식었을 때, 제어 루프 지터 영향)가 필요하다. 24h 「제어 주기 놓침 0」은 좋은 증거지만 같은 숫자는 아니다 | 맞다. README 표는 gRPC 2행뿐. 내부 근거는 [EV-088](../../05_verification/verification_evidence.md#ev-088)의 facade `try_log` p50 159 ns·p99 191 ns(256 B, RT 커널, CPU 2, `powersave`, 따뜻한 반복 루프, 실행별 분위수 중앙값)와 EV-064~071의 부하 중 수락 지연뿐이고, 최대값·식은 캐시·지터 영향은 없다. 도구 `call_cost`·`LatencyHistogram`(`examples/support/perf`)은 재사용 가능 |
| 2 | RT 스레드의 글줄 경로가 없다. tracing 입력은 일반 스레드 전용. NanoLog·defmt처럼 서식 id와 인자만 RT에서 넘기고 서식은 나중에 만드는 길이 있으면 빈칸이 메워진다. Probe에도 쓸모(RT의 드문 글줄) | 맞다. `logger/sink.rs`: "General path only … never emit these events from RT threads". RT 글줄은 사용자가 `Record`를 직접 정의해야 한다 |
| 3 | 타입마다 `encode`를 손으로 쓴다. Foxglove SDK처럼 derive 매크로나 protobuf(prost) 연동이 있으면 받아들이기 쉽다 | 맞다. `Record`는 `const SCHEMA` + 손으로 쓴 `encode`. `Schema::descriptor`로 protobuf `FileDescriptorSet`을 붙일 수는 있으나 생성 도구·예제가 없다. `prost`는 이미 의존성에 있다 |
