## S1 하네스 — 2026-11-24

- `soak run --events <every_s>,<hold_s>,<release_s>`: 주기적으로 `mark_event`(창 ±30 s, 동시 6개·보호 바이트 링의 절반), 홀수 번째는 `release_s` 뒤 `release_event`, 나머지는 `hold` 만료.
- `soak reader <dir> <interval_s> <seconds>`: 다른 프로세스가 닫힌 파일을 새것부터 통째로 읽어 파일별 온전함(판독·찢김·payload·외부 기록·파일 안 연속성·손실 행)을 보고, 열기 전에 사라진 파일과 읽는 동안 지워진 파일을 센다. 회차마다 파일 시스템 여유도 남긴다.
- `soak inspect`가 남은 기록의 연속 구간(`runs`)을 낸다.
- `scripts/soak-mixed.py`: 위를 함께 돌리고 CLI `tail` 2개(제어 메타데이터 `--limit 500000`, 프레임 원본 `--limit 1500`, 정상 종료 시 다시 붙임)·GetStatus 주기 호출. 판정: S4 기준(거절·miss 0, RT 스레드 heap 0, 디스크 ≤ 링) + 조회 회차 전부 온전 + 구독자 수신·예상 밖 종료 0 + 상태 전부 응답 + 표시·해제 전부 수락 + 파일 온전 + **남은 기록 = 빈칸 없는 꼬리 + 표시 창과 겹치는 섬**.
- 리허설 1(`/dev/shm`, 20분, 링 1 GiB, 이벤트 300/600/300 s): 13개 중 12 Pass. 섬 2개가 각각 표시 2·3의 창과 겹침, 일찍 해제한 표시 1은 섬 없음. 조회 20회 온전(사라진 파일 2), 상태 40회, 최악 응답 1,357 µs. 실패 1건은 판정 오류 — soak 종료로 서버가 닫힐 때 끝난 `tail`을 예상 밖 종료로 셌다 → 부하 종료 시각 이후 종료는 제외. 해제를 표시보다 먼저 처리하도록 순서도 바꿈.
- 리허설 2(6분, 이벤트 120/200/60 s): 13개 모두 Pass. 구독 지연 p50 약 12 ms, 재접속 약 300 ms. 제어 채널은 CLI가 다 받지 못해 gap이 생긴다(TASK-024 S2와 같음, 판정에 쓰지 않음).
